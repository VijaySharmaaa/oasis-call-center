# Hardcoded Call Categorization Schema

Source: [`backend/src/services/geminiService.js:13-232`](../backend/src/services/geminiService.js) — the `CATEGORIZATION_SCHEMA` constant.

These 17 top-level categories and **196 sub-categories** are embedded directly in the Gemini analysis prompt and populate the `category` / `sub_category` fields on `call_analysis` and `calls`.

> Not to be confused with `call_category` / `call_sub_category` — that is the *dynamic* taxonomy stored in the `call_categories` Mongo collection and regenerated by `POST /api/analysis/generate-categories` and `POST /api/analysis/generalise-categories`.

**The dynamic taxonomy is switched off by default** (`DYNAMIC_CATEGORIES_ENABLED=false`, added 2026-08-17). While it is off, `call_category` / `call_sub_category` are derived server-side from the hardcoded pair below and validated against this schema, the two generator endpoints return 409, and the hourly worker no longer mints new `call_categories` entries. The hardcoded schema on this page is never gated — it is always what drives `category` / `sub_category`. See the [Known issues](#known-issues) section for the drift that prompted the switch.

**Last revised 2026-08-14** — 14 sub-categories added and 2 duplicates resolved, based on the UPTET email corpus. See [`email-taxonomy-fit.md`](./email-taxonomy-fit.md) for the evidence behind each change.

## Change log

### 2026-08-14 — evidence-driven revision (184 → 196)

Derived from 1,895 UPTET helpline emails; every addition clears the ≥3-item evidence bar the schema's own generator prompt imposes (`geminiService.js:528-531`). Full analysis: [`email-taxonomy-fit.md`](./email-taxonomy-fit.md).

**Duplicates resolved (−2).** The schema previously violated its own mutual-exclusivity rule:

| Sub-category | Was | Now |
|---|---|---|
| `Password Forgotten / Reset` | in both #3 and #11 | **#3 only** — the category name explicitly claims "Password" |
| `OTR ID Forgotten` (#3) / `OTR ID Forgotten / Recovery` (#11) | same bucket, two names | **#11 only**, as `OTR ID Forgotten / Recovery` — identifier recovery is account access |

The governing split is now: **#3 owns credential challenges** (OTP delivery, CAPTCHA, password), **#11 owns account access** (login methods, lockouts, identifier recovery, sessions).

> `Account Recovery Query` remains in #3 and sits close to #11's `OTR ID Forgotten / Recovery`. Not a duplicate — generic recovery vs. specific identifier lookup — but worth watching if the two start colliding in practice.

**Sub-categories added (+14).** Counts are matched rows in the 1,895-email corpus:

The most consequential is `Appearing Option Missing in Dropdown`: it separates a *portal defect* from the eligibility-query bucket `Final Year Appearing Candidate Entry`, which alone was carrying 207 rows (11% of all traffic). The defect is now countable instead of hidden inside a query category.

## Known issues

### Returned values are not validated against the schema

`categorizeRecording` snaps hallucinated `call_category` / `call_sub_category` values back to safe defaults, but `category` / `sub_category` receive only a cosmetic `cleanCategory()` prefix strip. There is no check that the returned pair actually exists in `CATEGORIZATION_SCHEMA`, so whatever Gemini emits is persisted as-is.

Measured against the 45,162 completed analyses on the cluster (2026-08-17 audit): **65.0% of rows are an exact schema match**, 27.4% are the two dispositions below, 1.5% carry a valid category with an off-schema sub-category, and **6.0% carry a category name that is not in the schema at all** — 292 distinct invented names. Off-schema output rose from 0.2% of calls in March to 15.9% in May, which is what prompted `DYNAMIC_CATEGORIES_ENABLED`.

Note that the flag protects `call_category` only: with the dynamic taxonomy off, a pair that is not in `CATEGORIZATION_SCHEMA` snaps to `Uncategorised` / `-` before it can reach `call_category`. The underlying `category` / `sub_category` fields are still written unvalidated — closing that gap is a separate change.

### Two values bypass the schema entirely

| Value | Written by | Condition |
|---|---|---|
| `Call too Short` | `analysisWorker.js:104-113` | Call duration > 0 and < 10 seconds — skipped before Gemini is called |
| `Audio Unclear` | Gemini, via prompt special case (`geminiService.js:906-920`) | Audio too noisy, silent, or unintelligible to identify the issue |

Both are excluded from the summary corpus fed to `/generate-categories` (`analysis.js:549-553`).

These are **dispositions, not categories** — a distinction the schema does not yet model. See the disposition-axis recommendation in [`email-taxonomy-fit.md`](./email-taxonomy-fit.md#1-dispositions-belong-on-their-own-axis).

### The schema is call-shaped

`Call Back Request`, `Unrelated / Wrong Call`, `Repeated Call / Follow-up`, and `Helpline Timing Query` are all phrased for voice calls and cannot match an email — which is why #17 General Enquiry scored zero hits across the entire email corpus. Unresolved; see the channel-neutrality recommendation in the analysis doc.
